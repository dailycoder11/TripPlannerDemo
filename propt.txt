# Build Prompt: Phase 10 — City Tourism News Service

Implement Phase 10, **City Tourism News**, for the existing Daytrip application. Treat the current repository and branch as the source of truth. Inspect the app, existing services, configuration, README, dependency versions, and tests before changing code. Preserve the existing trip-planning flow, prompt-injection protections, booking service, policy search, and all existing files and branches. Do not push unless explicitly requested. Do not send news content to the itinerary-planning model.

## Product goal

Add a separate local News Service that gathers tourism-related news for five configurable Indian cities and stores a searchable snapshot in a file-backed relational database. In the planner, let users open city news from a compact **News** panel on the right. This panel must not take over the main planning page or submit/change the trip form. The existing policy search stays on the left; keep a visible **📚** control so policy search remains available when the native left sidebar is collapsed.

The service is a regular data service, not an agent. It does not call an LLM and does not generate or interpret news.

## City configuration and date windows

- Default to Shimla, Manali, Jaipur, Agra, and Udaipur. Keep this list in `news_service/config.json`, not in UI logic.
- At service startup, calculate date windows from the current date. Search the previous twelve fully completed calendar months in four consecutive three-month windows, plus a comparison window for the same three-month period one year earlier as the latest of those four windows.
- For example, on 1 November 2026, the four windows are November 2025–January 2026, February–April 2026, May–July 2026, and August–October 2026; also fetch August–October 2025 for the year-over-year comparison. Do not hard-code these example dates.
- Search for tourism news for every configured city and each window. Request no more than ten results per city/window. Keep dates inclusive and consistent across provider queries and API responses.
- Make the window-generation logic deterministic and unit-testable with an injected/current date.

## Search provider and cost controls

- Use Tavily Search API for news, with the news topic, explicit publication date bounds, basic search depth, and a maximum of ten results per request.
- Before implementation, consult Tavily’s official, current API and pricing documentation. Use only the free allowance. Do not require a paid plan or payment method, configure paid overages, or fall back to another paid provider. If the free allowance is exhausted or Tavily fails, stop the refresh and retain the last complete database snapshot.
- Read `TAVILY_API_KEY` from the environment or local `.env` file. Never hard-code, expose in the UI, or log the key. Do not perform a live search during development/tests unless a key is already configured and a live request is explicitly part of the authorized task.
- Validate provider response shapes, deduplicate URLs within each city/window, retain only valid `http`/`https` links, and safely handle missing titles, excerpts, source names, or publication dates.

## News Service, database, and HTTP API

- Add an independent FastAPI service in `news_service/`, bound to `127.0.0.1` by default on port `8003`.
- Keep host, port, city list, database path, result limit, request timeout, and search depth configurable.
- Use Python’s built-in SQLite support with a default database at `news_service/data/news.sqlite3`. Store refresh/window metadata and each article’s city, date window, title, short excerpt, original URL, source hostname/name, publication date when available, and fetch timestamp. Keep the file easy to inspect with a VS Code SQLite viewer. Do not add a database server.
- At startup, clear/replace the previous snapshot only after all requested searches have succeeded. Fetch all data first, then replace rows in a single transaction. On any provider or persistence failure, roll back and serve the previous complete snapshot. If no complete snapshot exists, report unavailable readiness and return no partial data.
- Expose `GET /health` with readiness, last refresh status/time, counts, and any safe non-secret error summary.
- Expose `GET /api/v1/news?city=<city>` with case-insensitive city matching. Return whether data is available, whether a prior snapshot is being served after a failed refresh, and two sections: the latest completed three-month period and its same-period-last-year comparison. Include each window’s start/end dates and up to ten articles. Unknown/unconfigured cities must return a clear unavailable/unsupported response without fabricated data.
- Keep the local demo unauthenticated and loopback-bound by default. Document that network exposure requires authentication and access controls.
- Log refresh outcomes, window/city counts, and safe status details. Do not log API keys or full article bodies.

## Streamlit UI behavior

- Reuse the existing destination and trip-date fields. Keep news separate from the itinerary prompt, planner form submission, and booking flow.
- Show no tourism-news control when the destination is blank, unsupported, or has no city snapshot. Show a compact, right-aligned **📰 News** control only when the service says that city has data. Opening it should display a popover/panel with **Current news** and **Last year, same time**, window dates, and each article’s title, excerpt, publication date when known, source name, and clickable original link.
- News must not occupy the planner’s main page by default. Keep the panel on the right side of the app; policy search stays on the left. Style the News and **📚** Policy controls with a light background and dark readable text, including hover and keyboard-focus states, consistent with the app theme.
- If the service is unavailable, do not block or interrupt trip planning. Show a brief status only where appropriate; do not display a misleading News control for unsupported destinations.
- Escape provider text before HTML rendering. Render links only when they use `http` or `https`.
- Never pass article text, links, or news-service output to the planning agent.

## Configuration and documentation

- Configure the app’s service URL with `DAYTRIP_NEWS_URL`, defaulting to `http://127.0.0.1:8003`.
- Add `TAVILY_API_KEY` and `DAYTRIP_NEWS_URL` to `.env.example` with a placeholder and local default. Ensure `.env`, SQLite databases, and other local secrets/data stay out of Git.
- Update `README.md` with Phase 10 behavior, default cities, provider/free-allowance setup and limits, date-window calculation, database location and VS Code viewing guidance, exact commands to start the News Service and Streamlit app in separate terminals, health/API examples, UI behavior, and last-good-snapshot handling. Explain that startup refreshes consume Tavily credits and paid requests are not made.
- Ensure the root `propt.txt` contains only this Phase 10 build prompt.

## Tests and verification

Add focused tests for:

- Date-window boundaries, including the 1 November 2026 example and year transitions.
- Five configured cities and the expected per-city/window search count.
- Provider request parameters, basic search depth, and max-ten limit.
- Response validation, URL safety, and URL deduplication.
- SQLite snapshot persistence and transactional rollback that retains the old snapshot after a failed refresh.
- API responses for supported/unsupported cities, ready/unavailable state, and last-good-snapshot status.
- UI states for blank/unsupported city, supported city with data, right-side News popover placement, and policy access when the sidebar is collapsed.
- Ensure news requests do not modify planner form state or reach the planning/booking services.

Run the focused and existing test suites, Python compilation, JSON/config validation, and a Streamlit app smoke check. Do not make a live Tavily request unless a valid key is already configured and the task explicitly authorizes it. Report precisely what was checked and any remaining setup or limitations.

## Constraints

- Preserve all existing files and branches; do not delete unrelated content.
- Preserve the existing policy-search behavior and its access from the visible **📚** control.
- Do not add a generative answer model, cloud vector store, live searches per user question, paid fallback provider, or news-to-agent connection.
- Keep user-facing language plain, show source links, and avoid presenting search snippets as verified facts beyond what the linked source supports.
