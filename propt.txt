Implement Phase 7: a separate dummy ticket-booking agent that communicates with the existing Daytrip agent over A2A.

First inspect the repository, current branch, and existing Phase 1–6 architecture. The current project is the Daytrip planning service. Preserve its existing behavior. If Phase7 does not exist, create it from Phase6 and make the changes there.

## Architecture: two independent services

1. **Daytrip service**
   - The existing Streamlit application remains the main agent and user interface.
   - It collects a ticket request, sends it to the booking service using an A2A client, and displays the booking service’s response.
   - It knows only the booking request and response formats. Do not put booking rules or booking policy logic in this service.

2. **Ticket-booking service**
   - Add a separately runnable service with its own process, configuration, and storage.
   - It is an A2A server that advertises its booking capability through an Agent Card.
   - It owns all booking rules, checks requests, creates dummy bookings, and calls an LLM to suggest changes when a request fails a rule.
   - Do not implement it as an imported Python module called directly by the Streamlit app. The two services must communicate over HTTP using A2A.

Use the current stable A2A specification and a compatible SDK if practical. Use A2A tasks and structured artifacts for request/response data. Do not substitute a custom REST endpoint or MCP for the agent-to-agent connection.

## Booking flow

1. Add a ticket-request section to Daytrip’s UI. Let the user provide the ticket/event name, event date, number of attendees, and amount per person in INR. Use the trip date and group size as sensible defaults when available.
2. Finish the existing Daytrip planning flow first, including its evaluation and critic steps. Do not show or enable the booking action while planning is still in progress.
3. Once planning is complete, show the user the relevant trip and ticket details. Only then show a button labeled **Continue booking**. Do not make this button available before those details are displayed.
4. When the user clicks **Continue booking**, Daytrip sends the ticket details to the booking service as an A2A task.
5. The booking service applies its configured rules:
   - For this phase, configure the minimum attendee count as `2`.
   - Configure the minimum amount per person as `500 INR`.
   - Keep these values in the booking service’s configuration. Daytrip must not read, duplicate, or enforce them.
6. If the request passes the rules, the booking service creates a dummy booking record and returns a structured confirmation artifact. Include a generated confirmation ID, event details, attendee count, amount per person, total amount, and booking status.
7. If the request fails a rule, the booking service calls its LLM to suggest a revised request that satisfies the failed rules. Return a structured proposal artifact containing the original request, suggested values, and a short explanation. Do not create a booking at this stage.
8. Daytrip displays the proposal and its full details. Show **Continue booking** only after those details are available. If the user clicks it, Daytrip resends the revised values to the booking service as a new A2A task.
9. The booking service checks the revised request against its rules again and creates a dummy booking only if it passes. If the user declines or leaves the proposal, do not create a booking.

The booking service must validate LLM suggestions deterministically before returning them. If the LLM fails, returns invalid data, or suggests values that still break the rules, return a clear structured failure response. Never let the LLM override or modify the configured rules.

## Credentials

- Use the same Groq credential already used by the Daytrip service: `GROQ_API_KEY`.
- The booking service must read the key from its own environment at startup. Document how to configure the same key for both services.
- Never send the Groq key in an A2A request, expose it in the UI, or write it to logs.

## Service boundary and local operation

- Keep the services independently startable and configurable. Add separate startup instructions for Daytrip and the booking service.
- Configure the booking service A2A URL through Daytrip configuration or an environment variable. Do not hard-code it.
- Keep booking records in the booking service’s own local JSON storage for this demo. Do not share the Daytrip memory directory or in-memory state.
- Use stable request or idempotency IDs so a repeated UI submission cannot accidentally create duplicate dummy bookings.
- Handle an unreachable booking service, malformed A2A responses, and LLM errors without crashing Daytrip. Show a clear error or unavailable state.
- Log the A2A task ID, final status, and confirmation ID where applicable. Do not log credentials.

## User interface

- Show the booking result as one of: confirmed, proposal awaiting user choice, declined, or unavailable/failed.
- For a proposal, show the suggested attendee count and amount per person, plus the reason for the change.
- Do not show **Continue booking** until the relevant trip or proposal details are visible and all preceding steps are complete.
- On proposal acceptance, show the final confirmation returned by the booking service. Do not display an accepted proposal as a confirmed booking until the booking service returns a confirmation.
