## Product goal

Give a Daytrip user a small chat-style interface for searching a curated collection of official travel and digital-service policy documents. The service should return relevant excerpts with enough source metadata to locate and verify them. It is a source-finding aid, not legal advice, a compliance checker, or a statement of Daytrip policy.

## Corpus

- Find and use approximately 6–10 current, relevant documents from official government, regulator, or service-provider sources.
- Cover practical travel topics and digital-service/consumer policies relevant to this application.
- Download PDF source files into `policy_service/documents/`; do not substitute generated summaries for source documents.
- Keep a machine-readable `policy_service/sources.json` manifest with a stable ID, filename, title, issuer, topic/category, source URL, publication date if known, effective date if known, retrieval date, and a short validity/context note for every document.
- Verify that each downloaded file is a readable PDF and that text extraction returns useful text. Record limitations such as scanned/image-only PDFs, missing dates, corrigenda, or future effective dates. Read amendments and corrigenda as related sources; do not imply a future rule is already in force.
- Prefer authoritative first-party sources and avoid presenting the documents as Daytrip commitments.

## Retrieval service

- Implement a standalone local FastAPI service under `policy_service/`; it is a retrieval service, not an agent and not a generative answer system.
- On startup, load the manifest and PDFs, extract text while retaining page numbers, split text into overlapping bounded chunks, create embeddings, and build an in-memory vector index. Rebuild the index from the local files on each service start.
- Use a public Hugging Face sentence embedding model suitable for semantic search (default suggestion: `sentence-transformers/all-MiniLM-L6-v2`). Cache/download it once. No Hugging Face authentication is needed for a public model. After the model is cached, embedding and search for user questions should work locally without per-question Internet access.
- Normalize embeddings and use cosine-equivalent vector search (for example, normalized vectors with FAISS inner product). Make model name, device, chunk size/overlap, result limit, similarity threshold, host, port, and manifest path configurable.
- Return matching source passages, not a fabricated or model-generated synthesis. A no-match result must be explicit. Deduplicate results sensibly while allowing multiple relevant documents/pages.
- Handle missing or unreadable individual PDFs with health warnings, and fail startup clearly if no usable passages can be indexed. Avoid logging user questions or sensitive content unnecessarily.
- Bind to loopback by default (`127.0.0.1`). This demo has no authentication; document that it must not be exposed to a network without adding access controls.

## HTTP contract

Expose and document:

1. `GET /health`: readiness, indexed document/chunk counts, model name, and non-fatal source warnings. Return an unavailable status when startup could not create the index.
2. `POST /api/v1/ask`: accept a JSON body with one bounded, non-empty `question` string; reject unknown fields and invalid input. Return the normalized question, `match_status` (`found` or `no_match`), at most two ranked matches, and a clear message. Each match should include document ID/title, issuer, category/topic, source URL, published/effective dates when known, validity note, retrieval date, page number(s), a similarity score, and excerpt. Log result IDs/pages/scores without logging question text. Do not add a hosted LLM, answer-generation API, or live web search to this request path.

## Daytrip UI integration

- Submit questions to the local Policy Service and render each match as a readable citation card with excerpt, title, issuer, page, date/validity context, and clickable official source link.
- Return and show only the top two matches. Include the retrieval similarity score in each result and the service logs. Label it in the UI as a similarity-based confidence score and explain that it is not a probability or guarantee of correctness.
- Style result text with explicit readable foreground and background colors; verify excerpts remain legible in both light and dark app themes.
- Show a clear no-match state and a helpful unavailable-service state. Validate the response shape before rendering; do not silently claim a search succeeded.

- Make the service URL configurable through the existing app configuration and an environment variable, with `http://127.0.0.1:8002` as the local default.
